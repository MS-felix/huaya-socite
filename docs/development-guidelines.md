你现在正在参与一个长期维护的正式项目。

你的目标不是“尽快写出能运行的代码”，而是：

- 保持项目架构稳定
- 最大程度复用已有代码
- 避免重复实现
- 建立清晰、统一、可长期维护的公共模块
- 让后续 AI 或开发人员能够快速理解和继续维护项目

在执行任何代码修改前，请严格遵守以下规则。

# 一、最高优先级原则

## 1. 先阅读，再开发

在编写任何新功能之前，必须先检查当前项目：

- `src/`
- `lib/`
- `utils/`
- `services/`
- `hooks/`
- `components/`
- `modules/`
- `api/`
- `store/`
- `types/`
- `constants/`
- `config/`

以及其他类似目录。

先确认项目中是否已经存在：

- 相同功能
- 相似功能
- 可以扩展的模块
- 可以复用的函数
- 可以复用的 Hook
- 可以复用的组件
- 可以复用的 API Client
- 可以复用的数据类型
- 可以复用的状态管理
- 可以复用的配置

如果已有实现可以满足需求：

**优先使用已有实现，禁止重新实现一套。**

如果已有实现只缺少少量能力：

**优先扩展已有模块，而不是创建新的重复模块。**

---

# 二、禁止重复造轮子

以下功能原则上必须统一封装，不允许在业务页面中重复实现。

包括但不限于：

## 网络请求

例如：

- GET
- POST
- PUT
- PATCH
- DELETE
- 请求 Header
- Token 注入
- Cookie
- 请求超时
- 错误处理
- API Base URL
- 请求拦截
- 响应拦截
- 401 / 403 处理
- API 错误格式化

必须统一通过项目的 Request / API Client 模块。

禁止在多个页面中直接重复：

```ts
fetch(...)
```

或者重复创建 axios instance。

---

## 用户认证

统一处理：

- 登录
- 登出
- Token
- Session
- Cookie
- 登录状态
- 当前用户
- 用户权限
- 用户角色
- 登录过期
- 未登录跳转

禁止每个页面分别请求：

```ts
/api/user
/api/me
/api/profile
```

获取当前用户。

应该由统一模块管理。

例如：

```text
auth
session
current-user
permission
```

---

## 文件上传

文件上传必须统一封装。

包括：

- 图片上传
- PDF 上传
- Excel 上传
- 普通附件上传
- 文件大小检查
- 文件类型检查
- 上传进度
- 上传错误
- 上传结果格式化

业务页面只应该调用类似：

```ts
uploadFile(file)
uploadImage(file)
uploadDocument(file)
```

禁止每个页面自行编写 FormData + fetch。

---

## 用户信息

例如：

- 当前用户
- 用户 ID
- 用户姓名
- 用户角色
- 用户部门
- 用户头像
- 用户权限

必须通过统一接口、Hook、Store 或 Context 获取。

禁止多个页面分别重复请求和处理。

---

## 权限

统一处理：

- 页面权限
- 菜单权限
- 按钮权限
- 操作权限
- 角色权限

不要在不同页面大量出现：

```ts
if (user.role === 'admin')
```

应优先抽象成：

```ts
can(...)
hasPermission(...)
usePermission(...)
```

或者项目已有的权限机制。

---

## 状态和常量

以下内容不能散落在页面中：

- 状态码
- 状态名称
- 枚举
- API 地址
- 路由地址
- 权限 Key
- 文件类型
- 业务类型
- 正则表达式
- 固定配置

应该集中维护。

例如：

```text
constants/
types/
config/
enums/
```

---

# 三、什么时候应该抽离公共模块

开发过程中，如果发现某段功能满足以下任意条件，应主动考虑抽离：

1. 已经在两个或两个以上地方出现
2. 很可能未来会在多个页面使用
3. 属于项目基础能力
4. 与具体业务页面没有强耦合
5. 包含重复的数据转换逻辑
6. 包含重复的请求逻辑
7. 包含重复的状态处理
8. 包含重复的权限判断
9. 包含重复的上传逻辑
10. 包含重复的表单处理
11. 包含重复的日期、金额、字符串处理
12. 包含重复的分页、筛选、查询逻辑

优先考虑抽离为：

```text
modules/
services/
hooks/
utils/
lib/
components/
```

具体位置根据当前项目已有架构决定。

不要为了“看起来模块化”而过度拆分。

只有存在明确复用价值时才抽离。

---

# 四、公共模块的职责必须单一

不要创建类似：

```text
utils.ts
common.ts
helper.ts
tools.ts
```

然后把所有东西放进去。

应该按功能拆分。

例如：

```text
lib/
  request/
  auth/
  upload/
  storage/

services/
  user/
  order/
  finance/

utils/
  date.ts
  money.ts
  string.ts

hooks/
  useCurrentUser.ts
  usePermission.ts
```

模块名称必须能够体现真实职责。

---

# 五、业务页面必须保持轻量

页面主要负责：

- UI
- 页面状态
- 用户交互
- 调用业务模块
- 展示数据

不要把大量：

- API 请求
- 数据转换
- 权限判断
- 文件上传
- Session 判断
- 复杂工具函数

全部写在页面文件中。

如果页面越来越长，应判断是否存在可以抽离的逻辑。

---

# 六、修改现有模块的规则

修改已有公共模块之前：

先分析：

1. 当前模块被哪些地方使用
2. 修改是否可能影响已有功能
3. 是否可以向后兼容
4. 是否可以通过增加参数或能力实现，而不是破坏原行为

禁止为了当前一个页面的需求，随意修改公共模块导致其他页面行为发生变化。

如果必须修改公共模块：

必须保持 API 尽量兼容。

---

# 七、禁止随意改变项目架构

除非有明显技术问题，否则不要擅自：

- 更换状态管理库
- 更换 HTTP 请求库
- 更换 UI 组件库
- 更换表单库
- 更换认证方案
- 更换目录结构
- 大规模重命名
- 大规模重构
- 引入新的架构模式
- 新增功能重复的第三方依赖

如果项目已经有解决方案：

继续使用现有方案。

不要因为你更熟悉另一个方案就进行替换。

---

# 八、引入第三方库的规则

安装任何新的 npm package 前必须先检查：

1. 项目是否已有相同能力
2. 原生 JavaScript / TypeScript 是否能简单实现
3. 当前 UI / 工具库是否已经支持
4. 是否真的值得增加依赖

如果一个几十行以内的简单逻辑可以完成：

不要随意增加第三方库。

如果已有第三方库已经能实现：

禁止再次安装功能重复的库。

例如已经有：

```text
dayjs
```

不要再安装：

```text
moment
date-fns
```

除非有明确必要。

---

# 九、类型统一

如果项目使用 TypeScript：

禁止为了方便大量使用：

```ts
any
```

公共数据结构应该统一定义 TypeScript 类型。

例如：

```text
User
ApiResponse
Pagination
UploadResult
Permission
```

如果类型已经存在：

必须复用。

不要重复创建：

```ts
UserInfo
CurrentUser
LoginUser
UserData
```

如果它们实际表示同一个对象。

---

# 十、统一 API Response

如果项目有统一 API Response 格式，例如：

```ts
{
  success: true,
  data: {},
  message: ''
}
```

那么必须继续使用。

不要在不同接口创造不同格式。

前端请求模块也应该统一处理：

- success
- data
- message
- error
- status

---

# 十一、错误处理

不要在每个页面自己设计一套错误处理。

例如：

请求失败：

统一经过 Request 层。

上传失败：

统一经过 Upload 模块。

认证失败：

统一经过 Auth 模块。

表单错误：

使用项目已有的表单机制。

业务页面只处理真正属于业务的错误。

---

# 十二、开始编码前必须执行的检查

每次接收到新的开发任务时，先进行以下分析：

### Step 1

搜索当前项目是否已有相关模块。

### Step 2

确定：

```text
可直接复用
可扩展
需要新建
```

属于哪一种。

### Step 3

检查是否会产生重复代码。

### Step 4

检查新功能以后是否可能被其他页面复用。

### Step 5

决定模块应该放在哪。

### Step 6

再开始编码。

不要直接看到需求就创建新文件。

---

# 十三、编码完成后再次检查

完成任务后检查：

- 是否重复实现已有功能
- 是否存在重复请求代码
- 是否存在重复上传代码
- 是否存在重复用户状态逻辑
- 是否存在重复权限逻辑
- 是否存在可以明显抽离的代码
- 是否新增了没有必要的依赖
- 是否破坏了已有公共 API
- 是否使用了项目已有组件
- 是否使用了项目已有类型
- 是否保持代码风格一致

发现问题后主动修正。

---

开发任何功能时，以下能力必须首先检查是否已有：

```text
Request

Current User

Download

Modal
Table
Pagination
Search
Filter
Date
Money
Validation

```

这是整个项目的基础能力。

原则上不应该由业务页面自行重复实现。

# 十五、模块文档

如果新增一个重要公共模块：

建议同时创建简单文档。

例如：

```text
docs/modules/request.md
docs/modules/auth.md
docs/modules/upload.md
```

或者项目统一的：

```text
MODULES.md
```

文档至少说明：

```text
模块名称
用途
文件位置
主要 API
参数
返回值
使用示例
注意事项
哪些地方正在使用
```

这样后续其他 AI 开发项目时，应优先阅读这些文档。

---

# 十六、维护 MODULES.md

如果项目根目录存在：

```text
MODULES.md
```

在开发前优先阅读。

如果不存在，可以创建。

它用于记录整个项目已有的公共能力，例如：

```markdown
# Project Modules

## Request

Path:
src/lib/request

Purpose:
统一处理 HTTP 请求。

Usage:
request.get()
request.post()

Do not:
不要在业务页面直接创建新的 HTTP Client。


## Auth

Path:
src/modules/auth

Purpose:
登录、Session、当前用户。


## Upload

Path:
src/modules/upload

Purpose:
统一文件上传。
```

以后每新增重要公共模块，都同步更新 MODULES.md。

---

# 十七、重要约束

不要为了完成当前需求而只关注当前页面。

需要同时考虑：

```text
当前需求
+
项目整体架构
+
已有模块
+
未来复用
+
维护成本
```

但也不要进行与当前任务无关的大规模重构。

遵循：

> 最小必要修改原则。

只修改完成当前任务真正需要修改的部分。

---

# 十八、禁止行为

严格避免：

```text
❌ 相同 API 请求逻辑出现多份
❌ 相同 upload 逻辑出现多份
❌ 相同 auth 逻辑出现多份
❌ 相同 currentUser 请求出现多份
❌ 相同 permission 判断出现多份
❌ 相同工具函数重复创建
❌ 重复创建相同 Type
❌ 重复定义相同 Enum
❌ 页面直接硬编码 API 地址
❌ 页面散落业务常量
❌ 为简单需求随意增加依赖
❌ 已有模块可以扩展却重新创建模块
❌ 为当前任务大规模重构无关代码
❌ 不检查项目直接开始编码
```

---

# 十九、决策优先级

当有多种实现方式时，按照以下顺序选择：

```text
1. 直接使用项目已有模块
↓
2. 扩展项目已有模块
↓
3. 将已有类似逻辑抽离成公共模块
↓
4. 创建新的公共模块
↓
5. 最后才考虑页面内部单独实现
```

---

# 二十、不要擅自发挥

没有明确需求时：

不要自行增加复杂功能。

不要自行改变产品逻辑。

不要自行改变 UI 交互。

不要自行修改数据库结构。

不要自行增加字段。

不要自行改变接口格式。

不要自行改变权限规则。

不要自行加入“可能以后有用”的复杂功能。

对于架构实现：

优先遵循当前项目已经形成的模式。

目标是：

```text
一致性 > 炫技
复用 > 重写
简单 > 复杂
现有方案 > 新方案
小范围修改 > 大规模重构
```

---

# 二十一、针对本项目建立基础模块

如果当前仓库仍处于项目初期，请首先检查是否需要建立以下基础模块：

```text
Request / API Client
Auth
Session
Current User
Permission
Upload
API Error Handler
Constants
Types
Storage
Notification
```

但是：

如果项目已经存在相同能力，不要重复创建。

在第一次整理完成后，创建或更新：

```text
MODULES.md
```

记录项目当前已经具备的公共能力。

---

# 最终执行原则

以后每当我要求你增加一个功能：

不要直接开始写代码。

先在内部完成：

```text
检查已有模块
→ 判断是否可以复用
→ 判断是否应该扩展
→ 判断是否应该抽离
→ 确定最小修改范围
→ 编写代码
→ 检查重复逻辑
→ 更新模块文档
```

如果发现已有公共模块：

优先使用。

如果发现多个地方存在相同逻辑：

优先抽离。

如果发现以后明显会被大量页面使用：

设计为公共模块。

如果只属于一个业务页面：

不要为了模块化而过度抽象。

始终保持整个项目：

**统一、简单、可复用、可维护、可扩展。**
